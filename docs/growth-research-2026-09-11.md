# アカウントを伸ばす方法の調査 — 2026-09-11

依頼: 「アカウントを伸ばすためにどうしたらいいか調査してください」。
数字は YouTube Analytics API v2 / Data API v3 で 2026-09-11 に取得した実測
（認証は `upload_youtube.get_credentials()`。**チャンネルへの投稿・変更は一切していない**）。
外部の事実は公式ページを本文で確認したものだけを「確認済み」と書く。

`docs/analytics-2026-09-10.md` の4点（寿命14日・ルートA閉鎖・登録者は対象外・
検索だけが腐らない）は**覆っていない**。本書はそのうち「検索」の大きさを実測し、
外部環境の変化（2027年2月の要件倍増）を加えて、優先順位を付け直したもの。

## 結論（先に）

1. **期限が付いた。** YouTube は 2026-08-10 に、**2027-02-01 以降の新規参加は
   8,000時間（または ショート2,000万回）**に倍増すると公式発表した。既存参加者は対象外。
   → **2027-01-31 までに 4,000時間を積んで申請を通す**のが、このチャンネルの
   収益化の実質的な最終ルート。過ぎたら必要量が倍になる。
2. **ショートの広告収益は、参加後も取れない。** 同じ発表で、参加済みチャンネルも
   ショートの収益分配には「直近90日1,000万回」の維持が必要になった。
   → 収益になるのは**長尺（ライブのアーカイブを含む）の広告だけ**。
   ショートの役割は集客に限られる、が公式に確定した。
3. **チャンネルには「腐らない動画」が実在する。** 2025-10-04 公開の
   「106万円の壁が2026年10月に撤廃」（`-uScWmzIt_E`）は、公開11か月後の今も
   **月1,000〜1,500再生**を検索から取り続けている（生涯 10,806 のうち検索 8,959 = 83%）。
   「バックカタログの価値はゼロ」は現行パイプラインの題材（国会答弁の引用）には
   当てはまるが、**「施行日のある制度改正 × 自分への影響」という題材には当てはまらない。**
4. **ライブ配信（実装済み・測定待ち）には、時間の計上と収益化審査の両方に穴がある。**
   4,000時間の計上は 2026-09-12 以降の測定で決まるが、通ったとしても
   **「読み上げただけのコンテンツ」は収益化ポリシーが名指しで除外している例**であり、
   審査はチャンネル全体を見る。ライブ配信を主戦力にするなら、審査時に
   チャンネルの中身が「読み上げ」に見えない形にしておく必要がある。

**推奨する順番**は末尾「やること」。一言でいえば、
**題材を「施行日のある制度改正」に寄せてショートと長尺を両方作り、
ライブは測定結果と審査リスクを見てから比重を決める。**

## 1. 外部環境: 2027-02-01 に要件が倍になる（確認済み）

YouTube 公式ブログ 2026-08-10 「New opportunities to earn and changes to the
YouTube Partner Program」と、ヘルプ「YouTube パートナー プログラムに関する変更」
（answer/12843009）で確認した。

| | 現行（2027-01-31 まで） | 2027-02-01 以降の新規参加 |
|---|---|---|
| 長尺の有効な総再生時間 / 365日 | **4,000時間** | **8,000時間** |
| ショートの視聴回数 / 90日 | 1,000万回 | 2,000万回 |
| 登録者 | 1,000人 | 1,000人 |

- 「This update won't impact creators already in YPP.」— 既存参加者は対象外
- 参加済みでも **ショートの収益分配には直近90日1,000万回の維持が必要**になる。
  下回っても長尺の広告収益は続く（ヘルプ原文:「対象となるショート動画の視聴回数に
  ついて、過去 90 日間で 1,000 万回を維持する必要があります」）
- **申請時点で判定するのか承認時点かは、公式ページに記述が無い**（未確認）。
  審査は「通常は 1 か月程度」（answer/12475004）。
  → 安全側に倒すなら **2026年12月末までに 4,000時間**、遅くとも 2027-01-31 までに申請。

### 必要な速度

現在地: `videoOnDemand 0.08 h / 9 views`（365日）。ショートの 12,950 h は計上されない。

| 目標 | 残日数 | 必要な長尺再生時間 / 日 | 24時間ライブなら平均同時視聴 |
|---|---|---|---|
| 2026-12-31 までに 4,000h（審査1か月を見込む） | 111日 | **36.0 h/日** | 1.50人 |
| 2027-01-31 までに 4,000h（申請期限ぎりぎり） | 142日 | **28.2 h/日** | 1.17人 |
| 期限を逃して 8,000h / 365日 | 365日 | 21.9 h/日 | 0.91人 |

見落としやすい点: **期限を逃しても1日あたりの必要量は 28 → 22 h/日にしか下がらない。**
どちらにせよ「平均して常時1人前後が長尺かライブを見ている」状態を作る必要がある。
ショートが1日 25.4 h の再生時間を生んでいる（`analytics-2026-09-10.md`）のと同じ桁。

## 3. ライブ配信の2つの穴（測定前に知っておくこと）

### 3-1. 計上の穴 — 「配信中の視聴」が入るかは公式に書かれていない

ヘルプ（answer/12475004）で計上外とされているのは
「限定公開、削除済み、または VOD（ビデオ オンデマンド）未変換のライブ配信」だけ。
設計書はこれを「公開でアーカイブが残れば加算」と読んだが、
**配信中の視聴時間が入るのか、アーカイブの視聴だけなのかは、原文では決まらない。**
二次情報（複数の解説サイト）は「配信中の視聴は含まれず、アーカイブの再生は含まれる」
と書いているが、一次情報ではない。

Analytics API の `creatorContentType` には `LIVE_STREAM` と `VIDEO_ON_DEMAND` の
別の値があり、`liveOrOnDemand` で LIVE / ON_DEMAND も分けられる（API リファレンスで確認）。
**9/12 以降の測定は、この2軸で分けて見ること。** HANDOFF の測定コマンドは
`creatorContentType` だけなので、`LIVE_STREAM` 行が増えて `VIDEO_ON_DEMAND` が
増えなかった場合に「入った」と誤読しうる。

```bash
python -c "
import sys, datetime; sys.path.insert(0,'scripts')
from upload_youtube import get_credentials
from googleapiclient.discovery import build
an = build('youtubeAnalytics','v2',credentials=get_credentials())
q = lambda **kw: an.reports().query(ids='channel==MINE', metrics='estimatedMinutesWatched,views', **kw).execute().get('rows', [])
for row in q(startDate='2026-09-08', endDate=str(datetime.date.today()), dimensions='day,creatorContentType', sort='day'): print(row)
for row in q(startDate='2026-09-08', endDate=str(datetime.date.today()), dimensions='liveOrOnDemand'): print(row)
for row in q(startDate='2026-09-08', endDate=str(datetime.date.today()), dimensions='video', filters='video==wWGQuS3yfXc'): print('archive', row)
"
```

2026-09-11 時点: Analytics は 9/08 分まで。9/09 の配信・アーカイブ（`wWGQuS3yfXc`、
Data API では 25 再生）は**まだ集計に出ていない**。`liveOrOnDemand` は `ON_DEMAND` のみ。

**注意**: 4,000時間の「対象となる」の判定は YouTube Studio の収益化タブの数字が
正で、Analytics の `VIDEO_ON_DEMAND` と同じである保証は無い。Studio の
「収益化」ページの進捗バーも併せて見ること。

### 3-2. 審査の穴 — 「読み上げただけ」は名指しで除外されている

チャンネル収益化ポリシー（answer/1311392、2025-07-15 改定後の本文）で確認:

- 収益化できない例: 「**ウェブサイトやニュースフィードのテキストなど、自分で作成して
  いない他の資料の内容を読み上げただけのコンテンツ**」
- 「クリエイターならではの、率直な洞察や視点が追加されておらず、汎用的または
  独創性のないテンプレートを使用して作成され、大量生産されたような印象を与える
  AI生成コンテンツ」
- 量産型の定義: 「テンプレートを使用して作成されたと思われるコンテンツや、同じ
  チャンネルの動画を続けて数本視聴した後、繰り返しのように感じられる可能性のあるコンテンツ」
- 収益化できる例: 「動画のイントロとエンディングは同じだが、コンテンツの大部分は異なる」
  「各動画が視聴者に創造的、教育的、その他の価値を提供」

ライブ配信は**設計上**「見出し・逐語引用・出典だけを読む」「引用カードのみ」「同じ57件を
約40分で繰り返す」。これは上の除外例に**そのまま**当たる。
審査は「自動システムと審査担当者によって、チャンネル全体が審査され」る（answer/12475004）
ので、ライブのアーカイブ（11.5時間 × 毎日）がチャンネルの動画本数の大半を占める状態で
申請すると、チャンネル全体が「読み上げ」と判定されるリスクがある。
合成音声・静止画のチャンネルが「再利用されたコンテンツ」で落ちる事例は二次情報で
多数ある（否認後の再申請は30日後）。

対して、ショートのナレーションは `script_writer.SYSTEM` が
「ニュースの要約ではなく、その発言・その数字が何を意味するかの解説にする」と指示した
モデル生成の解説文で、YouTube の言う「付加価値」に当たりうる。
**`work/<id>/script.json` にその台本は残っている**（ライブ設計書は「レシピに台本は
無い」としたが、work ディレクトリには残っている）。ライブ配信の読み上げを
逐語引用から「検証済みの解説ナレーション」に替える選択肢はある。
ただし一次資料に紐づかない文をライブに載せることになるので、
CLAUDE.md の関門との整合は別途判断が要る。**測定（3-1）が通ってから考える。**

## 4. 収益の桁（期待値を合わせておく）

参加できても、収益は**長尺の広告だけ**（1節）。24時間ライブに平均1人が
付いている状態は、1日あたり数十〜数百再生に相当し、広告収益は月に数百〜数千円の桁。
**ライブ配信は「参加資格を取る装置」であって「収益を生む装置」ではない。**

収益とチャンネルの寿命の両方に効くのは、2節の「施行日のある制度改正」型の長尺。
1本が検索で月1,000再生を11か月続けた実例が、59秒のショートで既にある。
同じ題材を 5〜8分の長尺で作れば、1再生あたりの再生時間は 2〜3分（ショートの3〜4倍）で、
かつ 4,000時間に計上される。

ただし**検索だけで 28 h/日は届かない**。チャンネルの検索流入は 90日で 3,682分（61時間）
＝ 0.7 h/日。長尺化で1再生の長さが4倍、題材の寄せで件数が数倍になっても、桁が2つ足りない。
→ **期限内の4,000時間はライブ配信が主、長尺は資産づくり**、が数字の上での役割分担。

## 5. 見送ったもの（理由つき）

- **冒頭維持率の A/B**（`2026-09-10-opening-retention-design.md`）: ショートの再生を
  約1.4倍にする施策で、4,000時間にも長尺収益にも直接は効かない。ショートが集客装置に
  なるのは長尺の受け皿ができてから。**順番を後ろに**。
- **登録者施策**: 要件は満たしており、ショートの収益分配は1,000万回/90日が必要なので
  登録者を増やしても収益ルートは変わらない。
- **過去動画のタイトル修正**: 答弁引用型は検索語を持たないので直しても拾われない。
  生きている7本は**そのまま触らない**（検索で当たっているタイトルを変えると落ちる）。
- **e-Stat 系統の復活**（`evidence.collect` のコメント）: 統計値を持つ題材は
  「自分への影響」型と相性がよいが、`getStatsData` の実装が要り、今回の期限には間に合わせない。

## 6. やること（順番）

1. **9/12 以降の測定を 3-1 のコマンドで行う。** `LIVE_STREAM` と `VIDEO_ON_DEMAND` を
   分けて読み、Studio の収益化ページの進捗も見る。
   結果が「配信中の視聴は入らない」なら、ライブは 11.5時間アーカイブの再生でしか
   積めないので、設計の前提から見直す。
2. **題材の選び方を「施行日のある制度改正」に寄せる。** 現行の `--keyword` 経路で
   国会会議録を直接引く（採用ゲートは変えない）。まず 2-4 の3束:
   - 社会保険の適用拡大（2026-10 賃金要件撤廃 / 2027-10 企業規模 51→36人）
   - 生活道路 30km（2026-09-01 施行済み。検索は続いている）
   - カスハラ防止義務 / インボイス
   タイトルは「**制度名 ＋ 施行時期 ＋ 影響を受ける人**」を含める（2-2 の生存パターン）。
   `Script.title` の生成指示を変えるだけで、採用ゲートには触らない。
   **効果の判定は再生数ではなく、公開30日後の `YT_SEARCH` 流入と、60日後に再生が
   残っているか**で行う（寿命14日を超えるかが問い）。
3. **同じ題材で長尺を作る**（`run_long.py --only A --only B --only C`）。3章を
   「賃金要件の撤廃 / 企業規模要件 / 週20時間の壁」のように**同じ制度の3論点**で組む。
   長尺 `UqjB--sNTKk`（5再生）は検索語を持たない題材だったので、比較対象にしない。
   タイトルは2と同じ規則。長尺は 4,000時間に計上されるので、1本ごとに
   `estimatedMinutesWatched` を記録する。
4. **ショートから長尺へ「関連動画」リンクを付ける。** YouTube Studio の
   コンテンツ → ショート → 関連動画（answer/14075157）。API では設定できず手作業。
   効果は流入元 `SHORTS_CONTENT_LINKS`（現在 90日で5）で測る。
   1日約2,500再生のショートから1%流れれば、1日25再生 × 数分。
5. **申請前にチャンネルの見た目を整える。** ライブのアーカイブが本数で支配しないよう、
   申請時にアーカイブを一時的に非公開にするかは、**1の結果と 4,000時間の内訳**を見て決める
   （非公開にすると、その分の時間は計上から外れる。ヘルプ原文の除外条件）。
6. 冒頭維持率の A/B は、3の受け皿ができてから。
