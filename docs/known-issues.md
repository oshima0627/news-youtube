# 既知の問題と未検証項目

実装完了時点（2026-08-11）で分かっている、**稼働前に片付けるべきこと**。
レビューで見つかったが今回の修正範囲外にしたものも含む。

## 1. 実データで採用0件になる（2026-08-12 解決）

`--dry-run` を実機で回したところ、**当日のRSS候補20件すべてが「根拠なし」で見送り**
になった。原因は検索語の作り方で、見出しから記号を除いた先頭40文字をそのまま
検索語にしていたが、国会会議録の全文検索（`any` は空白区切りのAND）では
40文字の長い文字列がヒットしない。

修正は3つを対で入れた。**どれか1つだけ入れると悪化する。**

1. **検索語を名詞2〜3語にする**（`scripts/keywords.py`）。janome で形態素解析し、
   固有名詞を優先して拾う。元号（令和・平成）は固有名詞として最優先で拾われるが
   題材を1ミリも絞らないので除外語に入れてある。
2. **題材の門番**（`keywords.is_policy_topic`）。国会で議論されえない見出し
   （天気・スポーツ・芸能）は一次資料に当てに行かない。当てても無関係な答弁しか
   返らない。
3. **該当箇所の切り出し**（`evidence.find_passage`）。発言全文（2,000〜3,000字）
   ではなく、**異なる検索語が同じ文脈に2語以上固まって現れる箇所**だけを引用に
   する。切り出せない発言は根拠にしない。

3番が関連性の関門そのもの。1番だけ入れた時点の実測では、当たるようにはなった
（12件中0件 → 12件中12件）が、消費税減税の見出しに憲法審査会の答弁、年金の
見出しにNISAの答弁が付いた。「検索語が発言のどこかに現れる」を関連性の判定に
すると、発言が長いぶん何も判定できない。

修正後の実測（2026-08-12、RSS 87件）: 門番を通った候補55件、上位14件を判定して
**11件で根拠が取れた**。引用は目視で全件が題材に沿っている。

**同じ日に同じ動画を2本作らない仕組みも同時に入れた**（`run_daily.py`）。RSSには
同じ出来事の見出しが各社から並ぶ（実測では消費税減税の見出しが4本）。発言URLの
重複除外だけだと、それぞれ別の発言（片山・大島・玉木・中野）が取れてしまって
素通りしたので、検索語が2語以上重なる題材も同じ出来事として落としている。

## 2. 手動CLI経路が引用の検証を通らない（2026-08-13 解決）

`write_script.py` → `build_short.py` を手で叩く経路は、`run_daily` にある
`ensure_grounded_card()`（`quote_excerpt` が一次資料の部分文字列かの検証）を
**通らない**。モデルが作った文字列が、一次資料の出典キャプション付きで
引用カードに描画されうる。

判定を `evidence.ground_excerpt` に切り出し、**カードを描く直前**
（`build_short.compose_base`）でも通すようにして塞いだ。

`compose_base` / `compose_stage` の `quote`（一次資料の逐語引用）は
**キーワード必須引数**にしてある。省略可能にすると、渡し忘れた経路が
検証なしで描けてしまい、同じ穴がまた空く。実際この変更で、逐語引用を
渡さずに引用カードを描いていた呼び出しが4件見つかった（すべてテスト内）。

`run_daily.ensure_grounded_card` も同じ関数を呼ぶ。あちらを残しているのは
差し替えを `script.json` に書き残すためで、画面と `script.json` が
食い違わないようにしている。

## 3. `figure` 有無の判定基準が2種類ある（2026-08-13 解決）

採用ゲートは厳格な `_FIGURE_RE.search()`、カードの出し分け
（`compose_stage` / `ensure_grounded_card`）は緩い `figure.strip()` を見ている。

現状 `figure` は常に空なので到達しないが、**統計系統を戻したとき**に
`figure="2024年度"` のような非数量文字列で採用が quote 側で通り、カードは
数値カード側に落ちる。するとモデル生成値に一次資料の出典が付く（問題1と同型）。

`evidence.has_figure()` に共有ヘルパ化し、採用ゲートと両方の分岐が同じ
基準を使うようにした。`figure="2024年度"` は数値カードに使われず、
引用カード側（＝逐語引用で検証される側）に落ちる。

統計系統を戻すときに気づける保証が無いので、到達しない今のうちに揃えた。
問題2と同型の穴なので、直し方も同じ「1つの関門を全経路が通る」形にしてある。

## 4. 画像の手動準備（2026-08-12 解決）

`work/<id>/photo.jpg` の `id` は見出しのSHA1なので、**明日の見出しを知らないと
事前に用意できない**。NHKのRSSは数時間で入れ替わるため、前日に用意しても翌朝
同じ候補が残っている保証がなく、無人実行の定常状態が「本日 0/2 本」になりうる
状態だった。

`scripts/commons.py` を足し、**発言者名から ja.wikipedia のその人物の記事画像**を
取るようにして解決した。人物名の全文検索（Commons 検索）は使っていない。
別人や集合写真が混ざっても、誰が写っているかを機械的に確かめる手段が無いため。
記事と人物は1対1なので、記事の代表画像なら写っている人物が確定する。
ライセンス（CC BY / CC BY-SA / CC0 / PD のみ）と大きさは Commons の imageinfo で
別途検証し、ダウンロードは従来どおり `photos.download` のホワイトリストを通す。

発言者の画像が取れないとき（政府参考人など）は国会議事堂の写真に落ちる。
実測11人中、8人が本人の顔写真、3人が国会議事堂だった。

なお、写真の切り取りは**上寄せ**にした（`build_short.PHOTO_ANCHOR_Y = 0.22`）。
縦長のポートレートを横長の写真枠（1080x659）に入れるので中央で切ると
頭の上が欠ける（高市早苗・櫛渕万里・平口洋の公式ポートレートで実際に欠けた）。
値は公式ポートレート5枚を描画して選んだ。上に寄せすぎる（0.15）と今度は
片山さつきの**顎**が下端で切れる。0.22 が5枚とも顔が収まる値。

## 5. 番組宣伝の見出しが題材として残る

「激動の政治・外交 記者たちが見た舞台裏」のような番組宣伝は、政策語を含むので
門番を通り、一次資料も取れてしまう（実測では「国際情勢が激動する中で」という
外務委員会の発言が付いた）。引用自体は無関係ではないが、**報じられた出来事が
無い**ので解説として成立しにくい。件数は少ないので保留にしてある。

**2026-08-13、これが実際に1本通って予約公開まで行った。** まさに
「激動の政治・外交 記者たちが見た舞台裏」の見出しから、日本ベルギー外交
160周年に触れた外務委員会の発言（`122103968X01020260513/27`）を根拠に
1本できた。一次資料は本物なので採用ゲートは正しく通っており、
**この形の失敗はゲートでは止まらない**ことがはっきりした。人手で気づいて
差し替えた（`unpublish.py` → `run_daily.py --limit 1`）。

門番（`keywords.POLICY` の対）に「舞台裏」「密着」などの語を足して落とす案は
まだ入れていない。1件しか実例が無い状態で語を並べると、「放送法改正」の
ような**本物の政策題材まで落とす**側の誤りが怖く、0本の日を増やす方が
このチャンネルには痛いため。実例がもう数件たまってから、共通する語で
判断すること。

## 5-b. 出席者名簿（会議録情報）が発言として採用されていた（2026-08-14 解決）

国会会議録APIは、各会議録の先頭に `speechOrder=0` / `speaker="会議録情報"` の
レコードを返す。中身は開会時刻と**出席者名簿**（委員・国務大臣・政府参考人の
氏名と役職）で、発言ではない。しかし2,000字近くあり、議員名・役職名・
「異動」「要求」などの語を大量に含むため、`find_passage` の近接判定を
いくらでも通してしまう。

**実測（2026-08-14）**: 「福岡 県が議員などの不当な要求から職員を守る条例案」の
検索語「福岡 議員 要求」で採用可12件のうち**12件すべてがこれ**で、切り出された
引用は参議院厚生労働委員会の出席者名簿だった（「福岡」は福岡資麿厚労大臣の姓に
一致していた）。採用されていれば、**出席者名簿に一次資料の出典キャプションが
付いた引用カード**が画面に出ていた。

`parse_speeches` で落とすようにした（`speechOrder == 0` または
`speaker == "会議録情報"`）。判定は「発言かどうか」というレコードの種別の話で、
題材の語彙を増やす話（5番）ではないので、実例1件でも入れてよい。
同じ検索語の採用可は 12件 → 1件になった。

**ただし残った1件も見出しとは無関係だった**（憲法審査会の臨時国会召集要求・
同性婚の答弁）。これは5番と同じ「ゲートは関連性を判定していない」側の問題で、
名簿を落としても消えない。

**2026-08-17、その残った1件がそのまま予約公開まで行った。** 同じ見出し
（「福岡 県が議員などの不当な要求から職員を守る条例案提出方針」）が同じ
検索語「福岡 議員 要求」で再びRSSに現れ、定例実行（06:00）が素で走って
`zC8OJmUT9Us`（当日18:30予約）を作った。引用は 5-b で名指ししていた
憲法審査会の答弁そのもの。**同じ見出しが数日おきに戻ってくる**ため、
「1回見送れば消える」たぐいの外れ方ではない。5番の番組宣伝
（2026-08-13）に続く2例目で、どちらも人手で気づくまで止まらなかった。

公開前に気づいて `unpublish.py zC8OJmUT9Us` で戻し、同じ枠を拉致問題の
中学生サミット（`1a01983b80ef`）で埋め直した。

**このとき、一度は「差し替えられる題材が無い」と判断している。** 候補20件の
うち採用可は6件で、噛み合っていたのは同日すでに使った1件だけだったため。
母数を45件（門番を通った全件）に広げると採用可は12件になり、噛み合う題材が
**21位以下に4件**あった。`run_daily.py` は既定で上位20件しか取り直さないので、
人が選ぶ経路もそこに縛られていた（`--candidates` で外した。
[`docs/daily-workflow.md`](daily-workflow.md) 参照）。
**「今日は当たりが無い」と言う前に母数を確かめること。**

## 6. テロップの割り付けを句読点の数で合わせていた（2026-08-12 解決）

当初は「本文を句読点で切った数」と VOICEVOX の `pause_mora` の数が一致する
前提で作った。最初の1本が25対25で一致したため成立していると考えたが、
**成り立たない**。VOICEVOX は句読点以外の場所にも間を入れる。翌日分を
作ったところ3本中2本で数が食い違い（23対26、28対30）、テロップが
まったく付かないまま静止字幕に落ちた。

**モーラ数で対応づける方式に変えた。** 区切りごとに読み方を引いてモーラ数を
数え、一括合成のモーラ列を同じ数ずつ切り分ける。読み方の総量は切って
数えても一括で数えても変わらないので、区切りの入り方に依存しない。
実測3本とも完全に一致した（495/486/494）。

## 7. 日をまたいだ重複を防げていなかった（2026-08-12 解決）

`state/seen.json` は見出しのSHA1しか持たないので、同じ出来事が翌日に
別の見出しで流れてくると素通りする。実際、初日に公開した「消費税減税」の
題材が、翌日分でも**同じ発言（出典URLまで同一）**を根拠にもう1本作られた。
重複除外が実行中のメモリにしか無かったのが原因。

`state/used.json` に直近14日ぶんの出典URLと検索語を残し、実行開始時に
読み込むようにした。同じ論点が数か月後にまた争点になることはあるので、
永久には禁止しない。

## 8. 予約済みの枠にもう1本載せてしまう（2026-08-13 解決）

枠は `pending_slots` が「まだ来ていない時刻」だけで決めていて、**その枠が
すでに埋まっているかを見ていなかった**。`upload_youtube.py` には重複防止が
無いので、埋まっている枠にもう1本アップロードすれば同じ時刻に2本並ぶ。

2026-08-13 に `--days-ahead` で 8/14・8/15 の4枠を先に埋めたことで顕在化した。
この状態で翌朝の定例実行（あるいはタスクスケジューラ）が走れば、そのまま
二重予約になる。作り置きをしなければ起きないので、それまで表に出ていなかった。

`state/published.json` の `publish_at` を見て埋まっている枠を外す
（`run_daily.taken_slots`）。読めないときは中止する — 「予約済みは無い」と
見なして進むのが、まさに防ぎたい失敗そのものだから。

**`unpublish.py` を対で直した。** 非公開に戻した動画の `publish_at` を記録から
落とす。残したままだと、YouTube 側の予約は解除されているのに記録の上では
枠が埋まったままになり、**その枠には二度と投稿されない**。

**実際に1件起きていた。** 8/12 の実行が作った「GPIF 平均4%の利回り」が
8/13 18:30 の予約を取っていたところに、8/13 の実行が同じ枠へ2本目を載せた。
気づいて2本目を空いていた 8/16 07:30 へ移した
（`upload_youtube.py <workdir> --schedule <時刻>`。再アップロードは起きない）。

**残っている穴:** YouTube Studio から**動画を消した**場合、記録には
`publish_at` が残るのでその枠は埋まったままになる。実際
`2D_cpARVcw0`（記録上は 8/13 18:30）が該当し、`videos.list` に出てこない。
`unpublish.py` を通さず消すとこうなる。困ったら
`state/published.json` から該当エントリを手で消すこと。
`videos.list` を引いて実在を確かめる手もあるが、run_daily は YouTube API を
直接叩かない設計（別プロセスの `upload_youtube.py` に寄せている）なので
入れていない。

## 9. クォータ超過を「チャンネル取り違え」と報告していた（2026-08-14 解決）

`current_channel` は `channels.list` が `HttpError` で落ちたとき `None` を
返していた。取り違えガードは `None` を「別のチャンネル」と同じ扱いにするので、
**確認できなかっただけの状態**が取り違えとして報告される。

**実測（2026-08-14）**: YouTube Data API の1日ぶんのクォータを使い切った状態
（403 `quotaExceeded`）で発動し、次の対処が表示された:

```
✗ アップロード先のチャンネルが指定と一致しません。
  期待: UCYHTfHJOoETzvpx-VZlUTng
  実際: 取得できず
  token.json を削除し、同意画面で正しいチャンネルを選び直してください。
```

**この指示に従うと正常な `token.json` を捨てることになり、しかもクォータは
1つも回復しない。** `run_daily.py` 側も「token.json が別チャンネルに
紐づいている可能性が高い」と報告して中止していた。

「別のチャンネルだった」と「確認できなかった」は別の事実で、対処も違う
（前者は認証のやり直し、後者は待つか通信を直す）。終了コードを分けた
（取り違え=3、確認不能=`EXIT_CHANNEL_UNVERIFIED`=4）。クォータ超過のときは
リセット時刻（太平洋時間0時＝JST 16:00〜17:00）と「token.json は消さないこと」
を出す。`None` を返すのは「認証は通ったがアカウントにチャンネルが1つも無い」
ときだけになった。

**クォータの目安**: 既定は1日10,000ユニットで、`videos.insert` が1本1,600。
1日3回の定例実行で2本作るぶんには足りるが、**`--days-ahead` で数日ぶんを
まとめて作り置きすると1日で使い切る**（8/12〜8/13 に6本上げた翌々日に出た）。
**ただしこの目安は実測と合わない日がある（下の10番）。**

## 10. 予約だけがクォータ超過で落ち、private の動画が取り残される

**2026-08-18 に発生。** `--keyword` で作った1本
（`MjkjrJVCN0w` / `work/2bff28f8a7d7`）で、1回目の private アップロードは
成功し、2回目の `--schedule`（`videos.update`、50ユニット）が
403 `quotaExceeded` で落ちた。動画は YouTube 上に private のまま残り、
`state/seen.json` には入るが `state/used.json` には入らない
（`save_used` は成功経路にしかない）。

**この状態は重複投稿の一歩手前だった。** `--keyword` は
`collect_news.py` を通らないので既出の除外がかからず、同じ検索語を
もう一度渡すと同じ内容がもう1本アップロードされる。既出の判定を
`run_daily` のループ内（**全経路が通る位置**）に移して塞いだ。

**クォータの消費が目安と合わない。** その日の枠（JST 16:00 リセット後）で
消費したのは、動画2本ぶん（`insert` 1,600 + `update` 50 + `channels.list`）と
3本目の `insert` で、単純合計は約4,900ユニット。10,000には届いていないのに
50ユニットの `update` が拒否された。**前日の同じ枠では6本（約9,900）が
通っている。** 原因は未特定。

- 消費の実際は Google Cloud Console の
  「APIとサービス → YouTube Data API v3 → 割り当て」で見える。
  **数字を推定で語らないこと**（この件の判断も、推定した4,900を根拠に
  「まだ余裕がある」と考えたのが外れている）。
- 取り残された動画は、リセット後に**再アップロードせず**予約だけ入れ直せる:
  ```bash
  python scripts/upload_youtube.py work/<id> --schedule <ISO8601>
  ```
  `published.json` の記録を使うので `videos.insert` は走らない（50ユニット）。

**2026-08-19 09:30 JST に同じ拒否が再発した。** 取り残されていた
`MjkjrJVCN0w` に予約だけ入れ直そうとして、`videos.update` が同じ
403 `quotaExceeded` を返した。この枠（8/18 16:00 JST 以降）でこちらが
走らせたのは動画1本ぶん（`insert` 1,600 + `update` 50 + `channels.list`）
だけだが、**前日夕方以降に他のセッションが何を消費したかは確認していない**
（数字を推定で語らないこと）。動画は private のまま無傷で、`token.json` は
正常。次のリセット（JST 16:00〜17:00）を待って同じコマンドを再実行する。

## 11. worktree で走らせるとアップロードだけが落ちる

**2026-08-19 に発生。** `.claude/worktrees/<name>/` で
`run_daily.py --keyword ...` を回したところ、台本・音声・動画までは
できたのに `upload_youtube.py` が `✗ client_secret.json がありません。`
で終了コード1を返した。`client_secret.json` と `token.json` は
`.gitignore` 済み＝**リポジトリ本体のチェックアウトにしか無い**ので、
worktree には最初から存在しない。

**run_daily はこれを「題材固有の失敗」として扱う。** アップロードの
