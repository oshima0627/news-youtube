# ライブ配信（24時間・ニュースラジオ）設計

2026-09-09。ニュースチャンネル `UCYHTfHJOoETzvpx-VZlUTng`（日本の最新ニュースまるわかり）で、
**一次資料の逐語引用だけを読み上げる16:9の常時配信**を24時間回す。
狙いは収益化要件の**有効な総再生時間4,000時間**を積むこと。

既存の日次パイプライン（`run_daily.py` / 採用ゲート / `state/published.json`）には一切触らない。
新規は `scripts/build_live_loop.py` と `scripts/run_live.py` の2ファイルだけ。

## なぜライブなのか（2026-09-09 実測）

```
channel: UCYHTfHJOoETzvpx-VZlUTng 日本の最新ニュースまるわかり
stats  : 登録者 2,910 / 動画 221本 / 総再生 1,341,662

=== 直近365日 ===
shorts             12,925.3 h   1,363,449 views
videoOnDemand           0.1 h           9 views

=== 直近90日 ===
shorts                789.3 h     103,169 views
videoOnDemand           0.0 h           5 views
```

収益化には2つのルートがあり、**現在地の遠さが2桁違う**。

| ルート | 現在地 | 要件 | 差 |
|---|---|---|---|
| Shorts 1,000万回 / 90日 | 103,169回 | 10,000,000回 | **約97倍** |
| 有効な総再生時間 4,000時間 | **0.1時間** | 4,000時間 | 平均同時視聴 **0.46人**を1年 |

4,000 ÷ (365×24) = **0.46**。「1年間ずっと平均0.5人が見ている」で届く。
チャンネルの流入は94.9%がShortsフィードで、**そのShortsは4,000時間に1分も寄与しない**
（下記ポリシー）。長尺VODは1本あるが累計5再生。**常時配信が唯一の現実的な経路**。

### ポリシーの根拠（YouTube公式ヘルプで確認）

- 4,000時間に**カウントされないもの**: 非公開・限定公開・削除済み・広告キャンペーン・
  **YouTube Shorts**・**「限定公開、削除済み、または VOD未変換のライブ配信」**
- 裏を返すと、**公開でアーカイブが残ったライブ配信は加算される**
- **アーカイブは12時間未満の配信でしか作られない。**
  「12 時間を超える配信については、アーカイブは作成されません」

→ **切らずに垂れ流すとアーカイブが1本も残らず、加算はゼロになる。**
これが本設計の形をすべて決めている。

## 素材は `recipes/*.json` だけ

**ライブ経路で新しい題材を取りに行かない。** 入力は既存のレシピ57件（2026-09-09 時点）に限る。

**理由**: レシピは全件が `evidence.collect()` の採用ゲートを通過済み。
ライブ側に採用ゲートを再実装すれば、判定基準が2箇所に分かれて必ず食い違う
（known-issues 2・3・8番と同型）。**ゲートは1つのまま、その出力だけを使う。**

## 読み上げるのは一次資料の逐語引用だけ

レシピにナレーション原稿は保存されていない（キーは `id / headline / keyword / category / evidence`）。
元の台本は復元できない。**ここでモデルに書き直させない。**

読むのは3つだけ:

1. `headline`（見出し）
2. `evidence.quote`（**一次資料からの逐語引用**）
3. `evidence.context` と `evidence.source_url`（出典）

**理由**: `evidence.quote` は採用ゲートが一次資料から逐語で取った文字列。
これだけを読めば、**この配信には創作された文が1文字も入らない**。
`ANTHROPIC_API_KEY` も不要。長尺で「導入と結びはモデルに書かせない」としたのと同じ判断を、
配信全体に広げた形になる。

### 尺（実測から算出）

```
引用文  57件  中央値 222字  合計 10,564字
narrate.SECONDS_PER_CHAR = 0.171
```

10,564 × 0.171 ≈ 30分。見出しと出典を足して **1周およそ40分**。24時間で約36周。
`run_daily.py` が毎日1件足すので1日あたり約40秒ずつ伸びる。

**これが本計画の最も弱いところ。** 11.5時間のアーカイブ1本に同じ内容が約17回入る。
量産型判定に対して弱い。厚みを増やす余地は `evidence.source_url`（国会会議録の全文）に
あるが、**まず40分で始めて実測してから足す**。実測なしに厚みを足すと、
効いたのがどちらか分からなくなる。

## 写真は使わない

`cards_wide` の16:9レイアウトは 見出し帯 / 写真 / 引用カード / テロップ だが、
**写真枠は使わず引用カードを主役にする。**

**理由**: `work/` に残っているのは8ディレクトリ（wav 7本・写真7枚）だけで、
57件中50件の写真は消えている。取り直すと**人物写真の取り違え**という、
このプロジェクトが最も警戒している事故を新経路に持ち込む
（CLAUDE.md「Commons の人物名 全文検索を使わない」）。背景配信で顔は要らない。

## 生成物

| パス | 中身 |
|---|---|
| `work/live/loop.mp4` | 16:9・h264+aac・全レシピ1周（約40分）。**毎日作り直す** |
| `state/live.json` | 現在の broadcast id / stream id / 枠の開始時刻 |

`loop.mp4` は順序をシャッフルし、その日までに増えたレシピを含めて毎日ビルドし直す。
**新しい `loop.mp4` を反映できるのはffmpegを再起動したときだけ**なので、
**1日2回のローテーションのうち片方（朝の回）でだけffmpegを止めて入れ替える。**
もう片方の回はffmpegを止めない。

**エンコードは1回だけ。** 配信は `-c copy` で再エンコードしない:

```bash
ffmpeg -re -stream_loop -1 -i work/live/loop.mp4 -c copy -f flv \
       rtmp://a.rtmp.youtube.com/live2/<固定キー>
```

**理由**: CPUがほぼゼロになり、日次パイプラインと同じPCで24時間回せる。

BGM は `bgm-youtube` の自前音源（Suno生成・自分の著作物）を低音量で敷く。

## 24時間サイクル：ffmpegは止めない。差し替えるのは枠だけ

```
liveStreams.insert（再利用可能なストリーム1本・キーは固定）
        │
        ├── ffmpeg ──▶ rtmp://.../live2/<固定キー>   ← 永久に流し続ける
        │
        └── 11.5時間ごと:  transition(complete) → アーカイブ確定
                           insert → bind → transition(live) → 次の枠
```

**11.5時間**は12時間上限に対する30分のマージン。24 ÷ 11.5 = 2.09 なので
**1日およそ2.1回転・年およそ760本**のアーカイブ。
ffmpegを止めない回は、映像が途切れるのは枠の切り替わりの数秒だけ。
1日1回だけ `loop.mp4` を入れ替えるためにffmpegを再起動する（下記）。

枠は `enableAutoStop: false` で作る（自動で終わられるとサイクルの制御を失う）。

## 関門（`run_live.py` の枠を作る関数の中に1箇所ずつ）

**呼び出し側に検証を置かない。** `upload_tiktok.post()` と同じ形にする。

| 関門 | 何を防ぐ |
|---|---|
| 二重起動ロック | `run_live.py` の二重起動で2本同時配信になる |
| 経過時間 11.5h 上限 | 12時間を超えてアーカイブが作られなくなる |
| 選挙カテゴリ除外フラグ | 投票日に選挙関連が流れ続ける（下記） |

**理由**: 重複投稿の関門をキューのフィルタ側にだけ置いた結果、直接叩く経路が
素通りした前例がある（known-issues 2・3・8番）。同じ穴を新経路に開けない。

## 失敗したときに何を守るか

**優先順位: アーカイブ > 配信の継続。**

| 起きたこと | どうする |
|---|---|
| ffmpeg が落ちた | 再起動する。回数上限を超えたら止めて通知 |
| APIが落ちて枠を切り替えられない | **12時間に達する前にffmpegごと止める** |
| クォータ超過で枠が作れない | 同上 |

**理由**: 配信を続けてアーカイブを丸ごと失うより、止めて11時間分を確定させる方が得。
12時間を超えた瞬間、その配信の再生時間は**1分も4,000時間に入らない**。

枠のローテーションは 1日2回 × 約150単位 = **約300単位**。日次パイプラインの
10,000単位に対しては小さいが、日次側が使い切った状態では配信が止まりうる。

## 投票日（公職選挙法129条）

**動き続けるライブ配信は継続的な公開行為**にあたる。ループに選挙関連のレシピが
混ざったまま投票日を跨ぐと129条に触れる。

→ `build_live_loop.py` に**カテゴリ除外**を持たせ、投票日は選挙関連を外したループに
差し替える。除外の判定は `recipes/*.json` の `category` を見る。

## テストで縛るもの

- ローテーション判定（11.5時間で切る純関数）— **12時間を超える経路が作れないこと**
- 二重起動ロック — 枠を作る関数を直接呼んでも素通りしないこと
- `loop.mp4` のビルドが引用文を**逐語で**載せていること（既存の `ensure_grounded_card` を通す）
- カテゴリ除外 — 除外指定したカテゴリのレシピが `loop.mp4` の素材一覧に入らないこと

## 最初にやること（実装より先）

**設計の前提が1つ未検証。ここが取れなければ設計ごと破棄する。**

1. 短い公開配信を1本流して終了し、**アーカイブが残るか**を見る
2. 数日後に Analytics を引き、**`videoOnDemand` の再生時間が増えているか**を見る
   （現在 0.1時間なので、増えれば一目で分かる）

## 未確認

- **公開ライブのアーカイブが `videoOnDemand` として4,000時間に計上されるか。**
  ヘルプの除外リストに載っていないことから推定しているだけ。**上記の実測で確かめる。**
- **ffmpegが流し続けている状態で、同じ再利用ストリームに次の枠をbindできるか。**
  仕様上できるはずだが未確認。駄目なら11.5時間ごとにffmpegも再起動する形に落とす
  （映像の断が数十秒に伸びるだけで設計は壊れない）。
- **`-stream_loop -1` と `-c copy` の併用でループ境界のタイムスタンプが飛ばないか。**
  飛ぶなら `-fflags +genpts` を足す。
- チャンネルでライブ配信が有効化されているか。`liveBroadcasts.list` はAPIとしては
  通った（既存枠0本）が、実際に配信できるかは1本流すまで分からない。
- **平均同時視聴0.46人が現実に取れるか。** 取れる根拠は無い。1年の賭けになる。

## やらないこと

- **既存ショートのループ配信をしない。** 公開済み動画の再利用配信は
  量産型ポリシーに正面から当たる。
- **採用ゲートをライブ経路に再実装しない。** レシピの出力だけを使う。
- **ナレーション原稿をモデルに書かせない。** 読むのは逐語引用と見出しと出典だけ。
- **写真を使わない。**
- **`run_daily.py` / `evidence.py` / `state/published.json` を触らない。**
- **`state/live.json` を手で編集しない。**
