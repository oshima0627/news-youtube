# チャンネル運用の自動化 — 設計

2026-08-13

制作パイプライン（`run_daily.py`）は完成して稼働している。この設計が扱うのは
**その外側** — 止まったことに気づく仕組みと、公開したあとの数字を制作に
返す仕組みである。

## 何を任せ、何を任せないか

任せる範囲は2つに絞る。

| 任せる | 任せない |
| --- | --- |
| 異常検知と自動復旧 | 視聴者対応（コメント返信・community） |
| 成果を見て改善（計測と提案） | 収益化要件・ポリシー逸脱の監視 |

右側は今回作らない。人格を伴う発信と、アカウントの生死に直結する判断を
自動化する前に、左側が安定して回っていることを確かめる。

## 実行環境の切り分け

3つの実行環境を、性質で割り当てる。**判断が要らないものにLLMを置かない。**

| 環境 | 割り当てるもの | 理由 |
| --- | --- | --- |
| ローカル（タスクスケジューラ） | 制作、指標の取得 | VOICEVOX・ffmpeg・`token.json` はローカルにしか無い |
| GitHub Actions | 停止の監視 | 判定は「直近7日に0本か」の一行。PCの状態に依存しない場所で走り、失敗するとメールが飛ぶ |
| Claude Code ルーティン | 改善提案 | 判断が要る。クラウドで動くのでローカル資源は使えないが、リポジトリは読める |

PCは常時起動する運用を前提にする（オーナーの決定）。ただし**その前提が
破れたときにこそ気づきたい**ので、監視だけはPCの外に置く。

---

# A. 停止の検知と自動復旧

## 監視するのは結果であって過程ではない

ログを監視すると「スクリプトは正常終了したがアップロードは失敗していた」
「PCごと落ちた」を取りこぼす。外から**チャンネルに動画が増えているか**だけを
見れば、原因が何であれ「止まっている」ことを捕まえられる。README が失格要因を
「止まっていること」と定義している以上、監視すべきはそこ。

## 認証を持たない

チャンネルの公開RSS（`https://www.youtube.com/feeds/videos.xml?channel_id=<id>`）
は**認証なしで公開日時つきに取れる**（2026-08-13 実測、15件）。YouTube Data API
のキーすら要らない。監視側に投稿権限どころか API キーも置かずに済む。

## 構成

**`scripts/watch_channel.py`（新規）** — 公開RSSを引き、直近 `--within` 日に
公開された動画を数える。0本なら終了コード1。ローカルでも手で叩ける。
RSSの解析は `sources.parse_feed` と同じ標準ライブラリで書く。

**`.github/workflows/watchdog.yml`（新規）** — 毎日 **12:00 UTC（21:00 JST）** に
`watch_channel.py --within 7` を走らせるだけ。失敗すると GitHub が既定で
リポジトリ所有者にメールを送るので、通知の仕組みを自前で持たない。

時刻の根拠は投稿枠との位置関係。その日の最後の枠（18:30 JST）が過ぎたあとに
見るので、当日ぶんの結果を当日のうちに判定できる。

**タスクスケジューラ（変更）** — 1タスクに 06:00 / 12:00 / 16:00 の3トリガー。

## 閾値は7日

収益化要件は90日で3本以上。7日は要件に対して十分早く、題材が無い日が数日
続いても誤報にならない。歩留まりの実測（2026-08-13）は候補20件中5件が採用可で、
枠1に対して5倍の余裕があった。この状態で7日連続0本なら明らかに異常である。

## 復旧はリトライ判定を作らずに実現する

**`run_daily.py` は冪等である。** 予約済みの枠には作らず 0.8秒で終了する
（`taken_slots`、2026-08-13 実装）。したがって定刻に3回走らせるだけで、
06:00 の一過性の失敗（ネットワーク・VOICEVOX の詰まり）は 12:00 が
18:30 の枠を埋めて回復する。

時刻の根拠は投稿枠（07:30 / 18:30）に対する位置。06:00 は朝の枠に間に合い、
12:00 と 16:00 は夕方の枠に間に合う。18:30 以降は埋めるべき枠が無いので走らせない。

**作らないもの:** 失敗状態の記録、リトライ判定、指数バックオフ。定刻起動で
同じ効果が出る。状態を持つほど、その状態が壊れたときの failure mode が増える。

# B. 成果を見て改善する

## 2週間は何も言えない

既存48本は形式が違い（AI台本 → 読み上げ → 画像貼り）、8か月の停止を挟んでいる
ので、いま作っている動画と比較できない。使えるのは 2026-08-13 以降のぶんだけで、
1日2本なら週に14本増える。

ここを曖昧にすると、数本のデータで自信ありげな提案が出る。それを採用すると
題材が偏り、似た動画が並び、**量産型判定に近づく** — 改善のつもりで最大の
リスクを踏む。「データが足りないうちは提案しない」を仕組みに埋め込む。

## 比較できる形で測る

公開直後の動画と1か月前の動画を並べても意味がない。**公開から7日経った時点の
数字を1本につき1回だけ記録する。** ショートは初速で大半が決まる。

**`scripts/collect_metrics.py`（新規・ローカル）** — 公開から7日を過ぎていて
まだ記録していない動画だけを取りに行く。記録済みかどうかで判定するので、
数日抜けても次回に拾われる（毎日走る必要すらない）。

起動は**制作とは別のタスクスケジューラのタスク**とし、毎日 21:00 に走らせる。
`run_daily.py` に相乗りさせない。相乗りすると、枠が埋まっている日は
`run_daily.py` が即座に return するので計測まで到達しないうえ、制作の
終了コードに計測の失敗が混ざって「何が失敗したのか」が読めなくなる。

取得するもの:

| 項目 | 出所 |
| --- | --- |
| 再生数・高評価 | `videos.list` の statistics |
| 視聴維持率（平均視聴率） | YouTube Analytics API |
| 検索語 | `recipes/<id>.json` の `keyword` |
| 題材・出典 | 同上 |

`yt-analytics.readonly` は既に `upload_youtube.SCOPES` に入っているので
**再認証は不要**（2026-08-13 確認）。

検索語を一緒に持つのが要点で、これがあるから数字を配点
（`sources.PLUS` / `MINUS`）に結び付けられる。

出力は `state/metrics.json` に追記してコミットする。**これがクラウド側から
読める唯一の経路である**（`token.json` はローカルにしか無いので、取得自体は
ローカルでしかできない）。

## 提案する側

**毎週月曜 00:00 UTC（月曜 09:00 JST）** のルーティンが `state/metrics.json` と
`scripts/sources.py` を読み、傾向を分析して**PRで提案を出す**。採否は人が決める。
適用が git の差分に残るので、いつ何をなぜ変えたかを後から追える。

提案には**必ず根拠の動画IDと数字を並べさせる**。「この語を上げるべき」だけでは
検証できず、レビューが追認になる。

比較可能な動画が **20本**（7日経過ぶん）に満たない間は、分析せず
「まだN本です」とだけ報告して終わる。1日2本なら10日ほどで到達する。

## 提案してよい範囲を限定する

| 触ってよい | 触らせない |
| --- | --- |
| `sources.PLUS` / `MINUS` の配点 | 採用ゲート（一次資料が無ければ公開しない） |
| `keywords.POLICY` への語の追加 | 重複除外の期間・条件（`USED_LOOKBACK_DAYS` 等） |
| `script_writer.SYSTEM` の調整案 | 引用の検証（`ground_excerpt`）、画像のホワイトリスト |

右側は品質と収益化の前提を守っている関門である。「伸びるから」を理由に
緩めてよいものではない。**成果の最適化が触れてよい範囲は最初から狭く固定する。**

## 壊れ方

計測の失敗は制作を止めない。別タスク・別スクリプトなので、YouTube API が
落ちていてもその日の動画は作られる。逆も同じで、制作が止まっても計測は
公開済みの動画を拾い続ける。

---

## 実装の順序

AとBは独立している。片方が壊れても他方は成立するので、順に入れる。

1. **A（監視と復旧）** — 制作が止まったことに気づけない状態を先に解消する。
   これが無いまま他を足しても、土台が抜けたままになる。
2. **Bの計測** — Aの直後に入れる。**データは時間でしか貯まらない**ので、
   提案側より先に動かし始める必要がある。1日でも早いほど提案の開始が早まる。
3. **Bの提案（ルーティン）** — 比較可能な20本が貯まる頃（2でおよそ10日後）に
   合わせて入れればよい。急ぐ理由が無い。

## テスト方針

既存のテストと同じく、外部（YouTube API・RSS）はすべてモックする。

- `watch_channel.py` — RSSの解析と日数判定を純関数に切り出し、固定のXMLで検証する。
  「0本なら終了コード1」「1本でもあれば0」の2点を押さえる。
- `collect_metrics.py` — 「7日未満は取りに行かない」「記録済みは二度取りしない」
  「取得に失敗しても既存の記録を壊さない」を押さえる。

## やらないこと

- 監視のためのダッシュボード。失敗時にメールが飛べば足りる
- 指標のグラフ化。判断はルーティンがやる
- 配点の自動適用。PRのレビューを挟む（オーナーの決定）
- 過去48本の取り込み。形式が違い比較にならない
