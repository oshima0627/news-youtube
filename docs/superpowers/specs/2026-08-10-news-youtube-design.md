# news-youtube 設計

チャンネル「日本の最新ニュースまるわかり」（`UCYHTfHJOoETzvpx-VZlUTng`）の
ショート動画を制作して YouTube に投稿するパイプライン。

## 前提となる調査結果（2026-08-10 時点）

| 項目 | 実測値 |
| --- | --- |
| 登録者 | 2,845人 |
| コンテンツ | ショートのみ（Studio の「動画」タブは0本） |
| 尺 | 56〜61秒 |
| ナレーション | VOICEVOX：青山龍星 |
| 最終投稿 | 2025-12-11（**約8か月停止**） |
| 稼働時の投稿 | JST 08:00 / 12:00 / 16:00 / 20:00 の1日最大4本 |
| 公開ショート48本の実績 | 合計 約38.2万回・平均 7,968回・中央値 4,583回 |
| 最高 | 3.6万回「中国がサンフランシスコ講和条約を無効宣言」 |

伸びた題材は**対中外交・政治家の発言・国内政策**に集中し、
下位は米中貿易など**日本の当事者性が薄いもの**だった。

### 収益化の状況

| 要件 | 現在 | 必要 |
| --- | --- | --- |
| 登録者 | 2,845 | 500 ✅ |
| 過去90日の投稿 | 0本 | 3本 ❌ |
| 有効ショート視聴（90日） | 4,465回 | 300万 ❌ |
| 総再生時間（365日） | 0時間 | 3,000時間 ❌ |

**登録者はクリア済みで、止まっていることだけが失格要因。**

### 制約：量産型コンテンツポリシー

2025-07-15 に YouTube の収益化ポリシーが「繰り返しの多いコンテンツ」から
**「量産型のコンテンツ」**へ改定され、収益化が許可されない例に以下が明記された。

> 説明、解説、教育的価値が最小限または皆無の画像スライドショー
> クリエイターならではの、率直な洞察や視点が追加されていない AI 生成コンテンツ

既存48本は「AI台本 → VOICEVOX読み上げ → 画像を貼る」という、この記述に
ほぼ一致する形式。**単純に同じ形で再開しても審査で落ちる可能性が高い。**

出典: <https://support.google.com/youtube/answer/1311392?hl=ja>

## 設計方針：一次資料先行型

RSSで題材を拾ったら、公開前に必ず一次資料を引きに行き、
**根拠となる数値か過去発言が取れた題材だけを採用する。**
取れなければ捨てて次の候補へ進む。

動画は「ニュースの要約」ではなく「その数字・その発言の解説」になる。
これにより、

- 独自性がパイプラインの構造として担保され、量産型判定を避けられる
- 語る根拠が一次資料なので、完全自動でも事実誤認が起きにくい
- ニュース記事を言い換えないため、翻案のリスクも下がる

代わりに題材は絞られる。数字も過去発言も絡まない純粋な炎上ネタは落ちる。
1日2本なら、候補を多めに拾って通ったものだけ使う余裕がある。

## アーキテクチャ

**1日1回まとめて作り、YouTube側の予約公開に載せる。**

タスクスケジューラは毎朝1回（06:00）`run_daily.py` を起動するだけ。
その1回で当日2本を作り切り、`--schedule` で 07:30 と 18:30 に予約して終了する。
PC が日中落ちていても YouTube 側が定刻に公開するため、
「完全自動なのに PC の稼働時間に縛られる」という弱点が消える。

**画像（`fetch_photo.py`）だけは自動ステップではない。** 題材ごとに写る人物・
場面が違い、ホワイトリストの中から適切な1枚を選ぶ判断が自動化できていないため、
前日までに手で当てておく運用になっている（実装後の実測を反映）。

```
（前日までに手動）
  fetch_photo.py        ホワイトリストから実写取得＋ライセンス記録
                        → work/<id>/photo.jpg + license.json

06:00  run_daily.py
  │
  ├─ collect_news.py    RSS巡回 → 候補20件（seen.json で既出を除外）
  │                     ※ subprocess で起動。全フィード失敗・候補0件は非0終了
  │
  └─ 候補を上から順に、当日の残り枠が埋まるまで
       ├─ evidence.collect()      ★採用ゲート（直接 import）
       │      国会会議録APIに当て、根拠（数値 or 逐語引用）＋出典URL が
       │      揃ったら採用、欠けたら次の候補へ
       ├─ 画像が無ければこの題材は見送り（上記の手動ステップ待ち）
       ├─ script_writer.write()   根拠だけを渡して台本生成（直接 import）
       ├─ narrate.synthesize()    VOICEVOX で音声合成
       ├─ build_short.build()     根拠カード生成 → 1080x1920 合成
       └─ upload_youtube.py       private アップ → --schedule で 07:30 / 18:30 予約
                                  ※ subprocess で起動
```

`run_daily.py` が `subprocess` で起動するのは `collect_news.py` と
`upload_youtube.py` の2つだけ。採用ゲートと台本生成は
`evidence.collect()` / `script_writer.write()` を**直接 import** して呼ぶ
（「環境不備なので即中止」と「この題材固有なので次へ」を例外の型で見分ける必要が
あり、終了コードだけでは足りないため）。
`verify_source.py` と `write_script.py` は、同じ処理を手で1件ずつ確認するための
単体CLIとして残してある（日次実行の経路には入らない）。

## コンポーネント

### collect_news.py — 題材の発見だけに使う

NHK（`cat0`/`cat4`）と Yahoo!ニュースの公開RSSを巡回し、`seen.json` で既出を
除外して候補20件を作る。

**RSSは「何が起きたか」を知るためだけに使い、記事の文章は台本に一切渡さない。**
内容は後段で一次資料から書き起こすため、記事の翻案にならない。

スコアは既存48本の実績に合わせ、対中外交・政治家の発言・国内政策に加点、
日本の当事者性が薄い題材に減点する。

出力: `work/candidates.json`

### evidence.py — 採用ゲート（`verify_source.py` は単体CLI）

判定の本体は `evidence.collect()`。日次実行は `run_daily.py` がこれを直接
呼ぶ。`verify_source.py` は同じ処理を手で確認するための薄いCLIで、
レシピの組み立て（`build_recipe()`）は両者で共有している。

候補を上から順に3系統へ当てる。

| 系統 | 使うもの | 取れる根拠 |
| --- | --- | --- |
| 発言 | 国会会議録API（`kokkai.ndl.go.jp/api/speech`、認証不要・JSON・100件/回） | 過去答弁の**逐語引用**＋会議名・日付 |
| 統計 | e-Stat API（要 appId・無料登録） | 政府統計の**具体的な数値** |
| 公表 | 各府省の報道発表 | 一次発表の**原文と日付** |

採用条件は「**出典URL** と **具体的な数値または逐語引用** の両方が取れること」。
片方でも欠けたら不採用にして次の候補へ進む。

2件そろった時点で打ち切り、そろわなければ本数を減らして続行する（無理に埋めない）。

出力: `recipes/<id>.json`

### fetch_photo.py — 取得元をホワイトリストで縛る（**手動運用**）

**このステップは自動では走らない。** `run_daily.py` は
`work/<id>/photo.jpg` と `license.json` の有無を確認するだけで、
無ければその題材を見送る。前日までにオーナーが手で当てておく。

| 出所 | ライセンス | 条件 |
| --- | --- | --- |
| `kantei.go.jp` | PDL1.0 | 出典明示＋「加工した旨と加工主体」の記載 |
| 各府省サイト | 政府標準利用規約2.0 | 出典明示 |
| Wikimedia Commons API | CC BY / CC BY-SA / PD のみ | クレジット必須 |

**ホワイトリスト外からは取得しない。** これにより、ウォーターマーク入りの
報道写真がそもそも混入しない（＝除去処理が不要になる）。

取得時に `work/<id>/license.json` を残し、`description.txt` に出典と
「加工した旨・加工主体」を自動で追記する。これは官邸規約が求める条件そのもの。

出典: <https://www.kantei.go.jp/jp/terms.html>

### script_writer.py — 根拠だけを渡す（`write_script.py` は単体CLI）

Claude API（`claude-opus-5`、adaptive thinking）に渡すのは `evidence.collect()`
が取った一次資料の抜粋のみで、RSSの本文は渡さない。

60秒＝350〜400字の話し言葉で、「ニュースの要約」ではなく
「この数字/この発言をどう読むか」を書かせる。
構造化出力（`output_config.format`）でタイトル・本文・タグを受け取る。

出力: `work/<id>/script.txt`, `work/<id>/meta.json`

### narrate.py / build_short.py

`narrate.py` は VOICEVOX のローカルエンジン（HTTP API）で**青山龍星**を使う。
既存2,845人の耳に合っている声を変える理由がないため継続する。

`build_short.py` は 1080×1920 で、上に実写、中央に根拠カード、下に字幕。
描画は `tora-kirinuki` の `draw.py` / `cards.py` を流用する。

根拠カードには必ず一次資料の出典キャプションが入るので、**カードに出す文字列は
一次資料に由来していなければならない**。一次資料が数値を持つ系統（統計・公表）
では数値カード（`render_figure`）、発言の系統（現状の唯一の系統）では逐語引用を
そのまま出す引用カード（`render_quote`）を使う。発言系で数値カードを使うと、
モデルが生成した値に一次資料の出典が付き、「一次資料が取れなければ公開しない」
という設計方針がそこだけ破れる。

字幕バンドに渡すのは `Script.subtitle`（40字以内）で、ナレーション全文ではない。
字幕は4行（実測で60文字あまり）しか描画しないため、400字のナレーションを渡すと
毎ビルド必ず切り捨て警告が出て、他の警告が埋もれる。

出力: `work/<id>/voice.wav`, `work/<id>/video.mp4`

### upload_youtube.py

`tora-kirinuki` からそのまま流用する。`expected_channel_id` ガードと
`--schedule`（YouTube側の予約公開）をそのまま使う。

### unpublish.py — 事後の緊急停止

完全自動で公開するため、公開後に問題が判明したときの手段を必ず用意する。

```
python scripts/unpublish.py <video_id>   # 即座に非公開へ戻す
python scripts/unpublish.py --all-today  # 当日分を一括で引っ込める
```

これが完全自動を選んだ場合の唯一の保険。

### run_daily.py — オーケストレータ

上記を順に回す。当日のスロット計算・追いつき・ゲート不通過の扱いを持つ。

## データフロー

| ファイル | 役割 | git |
| --- | --- | --- |
| `state/seen.json` | 既出題材のハッシュ。同じニュースを二度扱わない | ○ |
| `recipes/<id>.json` | 採用確定データ（題材・根拠の逐語引用・出典URL・使用画像とライセンス） | ○ |
| `state/published.json` | 投稿済みID・予約時刻・チャンネルID | ○ |
| `work/<id>/` | 台本・音声・動画などの中間物 | ✗ |

`recipes/<id>.json` が**再現の単位**。これさえ残っていれば動画を作り直せる。

## エラー処理

- **PCが落ちていた日** — 起動時に現在時刻から「当日のまだ来ていないスロット」だけを
  計算して埋める。**過去分は遡って埋めない**（古いニュースを今出しても伸びず、
  量産型の印象を強めるだけ）。18:30 を過ぎて起動した日はその日を捨て、翌朝に回す。
- **ゲートを誰も通らない日** — 本数を減らす。0本の日もあり得る仕様。
  ただし収益化要件が「90日で3本以上」なので、`state` に連続0本の日数を記録し、
  3日続いたら実行ログに警告を出す。
- **RSSの障害** — フィードが1つでも生きていれば続行する。**全フィードが失敗**
  または**候補が0件**なら、`collect_news.py` が原因を stderr に出して非0終了し、
  `run_daily.py` はそれを環境不備として中止する（空の候補で静かに0本にしない）。
- **一次資料APIの障害** — 落ちている系統だけスキップし、残る系統で判定を続ける。
  全系統が失敗したら `EvidenceSourcesUnavailable`。ただし系統が1つしかない今は
  「1回のタイムアウト」がそのまま「全系統ダウン」になるため、
  `search_speeches` 側で指数バックオフの再試行を行い、`run_daily.py` は
  **連続3候補で失敗**したときに初めて中止へ格上げする（1回の5xxで日を落とさない）。
- **VOICEVOX未起動** — 起動確認し、無ければ自動起動を試みる。
  それでも駄目なら中止する。**無音の動画は上げない。**
- **アップロード失敗** — `work/` を残して次回起動時にリトライ。
  API クォータは日10,000ユニットに対し `videos.insert` が1,600なので、
  2本/日＝3,200で十分収まる。ただし**1回目（private アップ）が成功した後**に
  `--schedule` が落ちた場合は既出（`seen.json`）に入れる。入れないと翌日また
  同じ題材を作って同じ動画をもう1本上げてしまう（`upload_youtube.py` に重複
  防止が無い）。private のまま手動公開待ちになる方が実害が小さい。
- **チャンネル取り違え** — `expected_channel_id` ガードを既存から流用する。
  発動時は専用の終了コード **3** を返し、`run_daily.py` はこれを環境不備として
  日次実行そのものを中止する。題材固有の失敗として次へ進むと、`token.json` が
  別チャンネルに紐づいている日に全候補で同じ失敗を繰り返した末、終了コード0の
  「本日 0/2 本」で終わって気づけない。
- **公開後の緊急停止** — `unpublish.py --all-today` は1本の失敗でループを
  止めない。失敗は記録して続行し、最後に「N件中M件成功」を出して失敗があれば
  非0終了する（唯一の保険が途中で止まると、残りが public のまま取り残される）。

## テスト

pytest。`tora-kirinuki` と同じ流儀。検証の中心は3つに絞る。

1. `verify_source` が根拠不足の候補を確実に落とすか
2. `fetch_photo` がホワイトリスト外のドメインを拒否するか
3. スロット計算が起動時刻ごとに正しい結果を返すか

この3つは壊れると「事故がそのまま公開される」箇所なので、ここだけは手厚くする。
